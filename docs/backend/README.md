# Backend Supporting Documents

Supporting documents for the backend layer delivered by the business team or tech team.

---

## Folder structure

| Folder | What goes here | Format | Claude-accessible? |
|---|---|---|---|
| `requirements/` | Business requirements, functional specs, acceptance criteria | Convert to `.md`; keep original alongside | Yes — `@import` into `backend/CLAUDE.md` |
| `design/` | Technical design docs, API specifications, OpenAPI/Swagger specs, sequence diagrams | `.md` for design decisions; PDF for diagrams | `.md` files — `@import`; PDF — prompt-only |

> **Note on API specifications:** OpenAPI specs (generated by Springdoc from the backend) live in `docs/backend/design/`. The frontend team references them here to understand available endpoints and generate typed HTTP clients. There is no separate `docs/api/` folder.

---

## How inline content and @imported documents work together

The `backend/CLAUDE.md` works as both at the same time — content you write directly into the file and documents you `@import` are loaded together as one combined context. Claude sees no difference between the two.

```
backend/CLAUDE.md (what Claude loads)
│
├── Inline content — written directly into the file
│   └── Tech Stack, Commands, Security Architecture,
│       Conventions, Layer Boundaries — stable, structured
│       content maintained here permanently
│
└── @import statements — pull in external documents
    └── @../docs/backend/requirements/your-requirements-file.md
        → Claude reads this file and treats it as part of
          backend/CLAUDE.md — indistinguishable from inline content
```

## What goes inline vs what goes in @imported documents

| What goes inline in `backend/CLAUDE.md` | What goes in `@imported` documents |
|---|---|
| Tech stack, framework versions, build tool | Full business requirements document from the business team |
| Commands (run, test, build, lint) | Detailed functional specification with all edge cases and scenarios |
| Key business rules (bullet summary — 5–10 rules) | Complete API specification from the tech lead |
| REST API endpoint list (brief summary) | Data dictionary or entity glossary from the DBA |
| Security Architecture table (STRIDE → Spring Boot controls) | Acceptance criteria per user story |
| Key Entry Points (real file paths) | Integration contracts for downstream consumers |
| Conventions and coding patterns | Any document that versions independently from the codebase |
| Layer Boundaries (what backend can/cannot call) | — |

**The rule:** stable, structured content you maintain as the codebase evolves stays inline. Documents delivered by other teams — which version independently — are `@imported`.

## How to use the `requirements/` folder

Store business and functional requirements documents here. Convert Word documents to Markdown so Claude can read them.

**Step 1 — Convert to Markdown and store both copies**

```
docs/backend/requirements/
├── [system]_business-requirements_v2.md     ← Claude reads this
└── [system]_business-requirements_v2.docx   ← original; human reference only
```

**Step 2 — Add `@import` to `backend/CLAUDE.md`**

```markdown
## Application Specification

@../docs/backend/requirements/[system]_business-requirements_v2.md

**Purpose:** Processes loan applications...  ← your inline content continues here
```

**Step 3 — When a new version arrives, update one line**

```markdown
<!-- update this line only: -->
@../docs/backend/requirements/[system]_business-requirements_v3.md
```

Claude picks up the new version immediately. Keep older versions — they are your audit trail.

## How to use the `design/` folder

Store technical design documents, API specifications, and sequence diagrams here.

### API specifications (OpenAPI / Swagger)

The backend exposes a REST API documented via Springdoc. The generated OpenAPI spec lives here so both the backend team and frontend team have one source of truth.

```
docs/backend/design/
├── [system]_openapi-spec_v1.yaml            ← Generated OpenAPI spec (Springdoc export)
├── [system]_openapi-spec_v1.md              ← Human-readable summary; @import for Claude
├── [system]_api-design_v1.md                ← API design decisions from tech lead
└── [system]_service-sequence-diagram_v1.pdf ← Sequence diagrams — prompt-only
```

**How the frontend team uses the OpenAPI spec:**

```
@docs/backend/design/[system]_openapi-spec_v1.yaml
Generate a TypeScript Angular HttpClient service for the /api/v1/applications endpoints
based on this OpenAPI specification.
```

**How to @import an API design document into `backend/CLAUDE.md`:**

```markdown
## Application Specification

@../docs/backend/design/[system]_api-design_v1.md
@../docs/backend/requirements/[system]_business-requirements_v2.md

**Purpose:** Processes loan applications...
```

### Technical design documents

Technical design documents from the tech lead or solutions architect define component responsibilities, sequence flows, and integration contracts. Convert to Markdown and `@import`.

```
docs/backend/design/
├── [system]_component-design_v1.md     ← @import into backend/CLAUDE.md
└── [system]_auth-flow-design_v1.md     ← @import into backend/CLAUDE.md
```

### Sequence diagrams and flow diagrams

Diagrams (PDF, PNG) cannot be `@imported` — reference them in the prompt when needed:

```
@docs/backend/design/[system]_service-sequence-diagram_v1.pdf
Does the error handling in LoanApplicationService.java match the failure path shown in this diagram?
```

## What NOT to @import

| Document type | Why not | What to do instead |
|---|---|---|
| Large vendor API guides (100+ pages) | Consumes context window on every conversation | Reference with `@` in the prompt only when needed |
| Full regulatory PDFs | Mostly irrelevant; obligations belong in `security/CLAUDE.md` | Keep in `docs/security/requirements/` |
| Binary files (`.docx`, `.xlsx`, images) | Claude cannot read them | Convert to `.md` first |
